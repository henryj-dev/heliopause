# 정책 평가를 워커로 — PR 2 의 설계 메모

`docs/policy-evaluation-realm-design.md` 가 측정과 결정을 들고 있다. 이 파일은 **그 결정을 코드로
옮기면서 정해야 했던 것**과 **그 근거**만 적는다. 측정을 다시 적지 않는다 — §번호로 가리킨다.

## 0. 무엇이 움직이나

평가 하나는 지금 **이 프로세스의 realm** 에서 돈다(`import()`). 그것을 워커로 옮긴다. 경계는
이미 #124 가 세웠다 — `evaluated` 가 **바이트를 돌려주고** 캐시가 바이트를 든다. 그래서 워커가
돌려줄 것의 타입은 **이미 `string`** 이고, 이 PR 은 그 문자열을 **다른 스레드에서** 만든다.

움직이지 않는 것: 스탬프 계산(`sourceStamp`), 캐시, 검증(`parsePolicySource`), 응답.
**존 검사는 움직인다** — 부모에 남지만 순서가 바뀐다. §6 에 적었다.
**스탬프는 부모가 잰다** — 워커가 파일을 다시 읽으면 두 번 읽고, 그 사이에 파일이 바뀌면 **캐시
키와 내용이 갈린다.**

## 1. 결정 1·2·3 — 채널·순서·캡처 (§3-b ①②③)

세 측정이 각각 한 줄을 정했다. 그 줄을 빼면 **전역을 안 건드리고도 위조가 도착한다.**

```
부모: const { port1, port2 } = new MessageChannel()
      worker = new Worker(evalWorker, { workerData: { /* 포트 없음 */ } })
      worker.postMessage({ reply: port2 }, [port2])      ← 초기 메시지로 전달
워커: const reply = await 첫 메시지                        ← import 보다 먼저
      const send = MessagePort.prototype.postMessage      ← 첫 import 보다 먼저 캡처
      ... 여기서부터 정책 모듈을 import ...
      send.call(reply, { ok: true, wire })
```

| 줄 | 빼면 | §3-b |
|---|---|---|
| `workerData` 에 포트를 **넣지 않는다** | 모듈이 `workerData.reply` 를 **읽어서** 보낸다 | ② |
| 포트를 **`import` 전에** 받는다 | 모듈이 `parentPort.once("message")` 로 **포트를 훔친다** | ② |
| `postMessage` 를 **첫 import 전에 캡처** | 모듈이 prototype 을 갈아 호출 시점 lookup 을 가로챈다 | ③ |

🔑 **그래서 이 셋은 「방어를 더한 것」이 아니라 「순서」다.** 같은 코드가 순서만 바뀌면 뚫린다 —
그것이 ② 표의 셋째 행이 측정한 것이다.

⚠️ **`parentPort` 는 결과 경로로 쓰지 않는다**(§3-b ①: 모듈이 그것으로 **먼저** 답한다). 부모는
`parentPort` 로 온 것을 **결과로 보지 않는다.** 다만 초기 메시지 자체는 `parentPort` 로 받아야
하므로, 워커는 **첫 메시지 하나만** 거기서 읽고 그 뒤로는 보지 않는다.

## 2. 결정 6 — 결과로 받는 것 (사용자 결정, 2026-10-07)

**전용 채널 + 스키마 통과 + 문자열(바이트)** 만.

바이트인 이유는 #124 가 이미 `Promise<string>` 이기 때문이다. 객체를 받으면 §10·§11 이 기록한
`then`·`toJSON` 질문이 **워커 경계에서 다시 생긴다** — 구조화 복제가 `toJSON` 을 부르지는 않지만
**부모가 그 객체를 resolve 하면 `.then` 을 읽는다.**

스키마: `{ ok: true, wire: string }` 또는 `{ ok: false, message: string }`. 그 모양이 아니면
**결과가 아니다.** `wire` 가 문자열이 아니면 거부한다 — 길이도 보지 않고 타입만 본다(내용 검증은
부모의 `parsePolicySource` 가 한다, 지금처럼).

## 3. 결정 7·8 — 결말, 그리고 grace 는 **셋으로 나뉜다**

검증을 통과한 **첫 결과를 즉시 채택해 응답**한다. 워커는 **상한 있는 grace** 동안 살려 두고, 그사이
`error`·비정상 `exit` 는 **`faults` 로 세고 로그만** 남긴다(응답도 캐시도 바꾸지 않는다).

🔑 **grace 가 있는 이유는 그것이 오늘 동작이기 때문이다.** 지금 모듈이 올바른 값을 준 뒤 비동기로
터지면 `uncaughtException`·`unhandledRejection` 핸들러가 **`faults` 를 올리고 서빙을 유지한다**
(`bin/heliopause-policy-render.ts:163-170`, `lateThrowFromModuleTimer` shape 이 `faults > 0` 을
단언한다). 결과를 받고 곧바로 종료하면 **그 가시성이 사라진다.**

⚠️ 이 문단은 설계 문서에서 한 번 **정확히 반대로** 적혀 있었고, 그 틀린 서술이 사용자 결정의 대가를
가린 채 전달돼 **결정이 한 번 뒤집혔다.** 그 기록은 §3-a 에 있다.

### 결말 셋 — **「실패에는 grace 없음」만 적으면 하나가 빠진다**

| 결말 | grace | 왜 |
|---|---|---|
| **유효 결과를 받았다** | **준다** | 늦은 결함이 숨을 수 있는 유일한 자리다 — grace 의 존재 이유 |
| **`error` · 비정상 `exit`** | **안 준다** | 이미 결말이 났다. 더 기다려도 **셀 것이 없다** |
| **타임아웃 · 동기 spin** | **안 준다 — 이유가 다르다** | 아무 이벤트도 안 왔고 **부모 타이머가** 결말을 만든다. 이미 budget 을 다 썼으므로 grace 를 더하면 **두 번 기다린다** |

🔴 **셋째를 따로 적는 이유**: 「실패에는 안 준다」로 뭉치면 읽는 쪽이 **둘째만** 생각한다. 그리고
셋째는 **비용의 방향이 반대다** — 둘째는 아낄 것이 없고, 셋째는 **이미 쓴 것 위에 더 쓰는 것**이다.

🔑 **그리고 이 기본값이 2라운드 발견의 비용을 없앤다.** 캐시는 **성공한 결과만** 담으므로(`:954` 의
`cached.set` 이 던질 수 있는 두 줄 **뒤**) **실패하는 사이트는 요청마다 재평가된다** — 독립 리뷰가
파일을 바꾸지 않고 `/source` 세 번으로 **503 세 번 · 평가 세 번**을 재현했다. 실패에 grace 를
주면 그 비용이 **「요청 빈도 × grace」**로 쌓인다. 안 주면 **쌓이지 않는다.**

### grace 값

**1,000 ms.**

⚠️ **측정이 아니라 선택이다.** 측정된 것은 §3-b ④ 하나다 — 모듈의 200 ms 타이머에 대해 **50 ms
종료 → `error` 안 옴**, **600 ms 생존 → 옴**. **관측 한 건**이고 분포를 모른다. 「1,000 ms 면 대부분
잡는다」는 **재지 않았다.**

🔴 **어떤 값도 전부 잡지 못한다** — 모듈은 타이머를 임의로 길게 걸 수 있다. 그러므로 이 값은
**「무엇을 잡는가」가 아니라 「얼마를 내는가」**로 읽어야 한다.

⚠️ **grace 는 응답 지연에 들어가지 않는다.** 응답은 첫 유효 결과에서 바로 나간다. grace 가 미루는
것은 **워커 회수**이고, 비용이 나타나는 자리는 **동시 워커 수와 메모리**다 → **#117**.

## 4. 이 PR 에서 정해야 했던 것 — **동시 워커 상한과 타임아웃**

§3-a 의 열 중 둘이 여기서 막혔다. 둘 다 **#117 로 넘긴 항목**인데, 코드가 값을 필요로 한다.

### 타임아웃 — **기존 값을 그대로 쓴다**

`SOURCE_SITE_BUDGET_MS`(env `HELIOPAUSE_POLICY_SOURCE_BUDGET_MS`)와 `READY_SITE_BUDGET_MS` 가
이미 있고 `evaluateWithin` 이 그것으로 타이머를 건다. **새 값을 만들지 않는다.**

🔑 **근거: 그 예산은 「평가가 끝나기까지」를 재는 것이고, 평가가 어느 스레드에서 도는지와 무관하다.**
새 env 를 만들면 **두 자리가 같은 것을 말하고 갈라진다** — 이 저장소가 반복 기록한 모양이다.

⚠️ **그러나 budget 이 끝났을 때 하는 일이 바뀐다.** 지금은 타이머가 **거절만** 하고 평가는 계속
돈다(같은 realm 이라 멈출 방법이 없다 — §11 의 「닫을 수 없는 하나」). 워커에서는 **`terminate()`
가 실제로 멈춘다.** 그래서 이 PR 은 **동기 spin 을 닫는다** — §4 가 그것을 쟀다
(`ERR_SCRIPT_EXECUTION_TIMEOUT` 이 아니라 `terminate()` 쪽, `exitCode=1`).

### 동시 워커 상한 — **세지 않고, 세는 자리를 만든다**

이 PR 은 **상한을 넣지 않는다.** 대신 **지금 뜬 워커 수를 세어 `/readyz` 에 싣는다.**

🔴 **근거는 「측정 없이 값을 고르지 않는다」다.** #117 이 적은 대로 `resourceLimits` 는 **그 워커의
힙**에 걸리고 컨테이너 한도는 **프로세스 전체**에 걸린다. 그 둘의 합이 넘치는 지점은 **배포의
메모리 한도**에 달려 있고, 그 값을 이 저장소에서 읽을 수 없다(`stardust-deploy` 의 매니페스트이고,
이 파일이 여러 번 「설정과 운영은 다른 것」이라고 적어 둔 그 경계다).

**그래서 순서는 이렇다**: 세는 것을 먼저 넣고 → 운영에서 최대치를 읽고 → 그 수로 상한을 정한다.
상한을 먼저 넣으면 **내가 고른 수가 측정 없이 운영에 들어간다.**

⚠️ **그 사이에 상한이 없다는 것은 적어 두어야 한다.** 동시 평가의 자연 상한은 둘이다:

| | 상한 |
|---|---|
| 기동 검증 | **사이트 수**(지금 넷) — 전부 동시에 평가한다 |
| 요청 경로 | **동시 캐시 미스 수** — 병합하지 않는다(2라운드 발견) |

→ **고장난 사이트에 요청이 몰리면 요청마다 워커가 뜬다.** 위의 「실패에는 grace 없음」이 **회수는**
즉시로 만들지만 **생성은** 막지 않는다. 그것이 상한이 필요한 이유이고, **#117 이 정할 것**이다.

늘어야** 한다.

## 6. 구현하며 정한 것과 잰 것

### 존 검사는 마지막으로, 와이어 위에서 (결정 A · A1)

워커 realm 은 모듈의 것이다. 그 안에서 `site.hosts[].id` 를 읽으면 getter 나 `Array.prototype` 교체로
검사가 통과한다. 그래서 검사는 **부모가 파싱한 와이어 데이터**에서 돈다. 대가는 존이 틀린 모듈도
**수집까지 끝난 뒤** 거부된다는 것이다.

그 순서 때문에 「이름은 맞고 내용이 깨졌다」(`ZoneCheckedError`)를 더는 말할 수 없다. 내용 실패는 늘
검사 전에 난다. 기동 로그는 **이름에 대해 아무 말도 하지 않는 한 줄**이 됐고(A1), `ZoneCheckedError`
와 그 `WeakSet` 은 도달 불가가 되어 지웠다. 진짜 존 불일치는 여전히 `exit 2` 다.

테스트는 문구가 아니라 속성을 단언한다: ① 이름 단서가 없다 ② 원인이 있다 ③ 진짜 불일치는 `exit 2`.

### 결말 분류 — exit 13 은 타임아웃이 아니다

최상단에서 아무것도 안 걸린 `await` 는 워커의 이벤트 루프를 비우고, Node 가 **exit 13**
(unsettled top-level await)으로 수 ms 안에 스레드를 끝낸다. 실측(node 26.4): 핸드오버 25 ms 뒤
`exit 13`, 3 s 예산은 발사 전. 핸들을 잡은 hang 이나 spin 은 예산까지 살고 `terminate()` 로 exit 1.

인프로세스 렌더러는 같은 모듈을 타임아웃으로 보고했다 — 공유 이벤트 루프가 타이머를 붙들고 있었기
때문이다. 워커는 그보다 먼저 사실을 안다. 그래서 결정 8(결과 없는 exit)로 분류하고 **원인을 적는다**.

### 우리의 `terminate()` 는 fault 가 아니다

`terminate()` 는 워커를 **exit 1** 로 끝낸다(실측: 답한 뒤 종료하면 1, 스스로 끝나면 0). 응답 뒤의
비정상 exit 를 늦은 결함으로 세는 핸들러가 그 1 을 세면, **핸들을 잡은 모든 모듈이 평가마다 fault 를
하나씩 올린다** — grace 가 지키려는 신호가 무의미해진다. 우리가 끝낸 exit 는 세지 않는다.

### 사이트 간 오염이 닫혔다 — 그리고 그 측정

`da80b7b`(워커 이전)에서 beta 가 `Object.prototype.toJSON` 을 오염시키면 **alpha·beta·`/readyz` 가
전부 503 「the answer could not be serialised」** 였다(던지는 `toJSON`·`undefined` 를 돌려주는 `toJSON`
두 모양 다). 워커에서는 **alpha 200 · `/readyz` 200(1/2 서빙) · beta 503**.

예전 테스트는 그 503 을 기대값으로 들고 있었다 — 「프로토타입을 오염시키면 모든 사이트가 503 인 것이
맞다」. 그것은 인프로세스 렌더러가 **자기 한계를 명세로 적은 것**이었고, 결함이었다. 기대값을 200 으로
바꾼 근거는 위 측정이다.

### `/readyz` 에 `workers`

지금 살아 있는 평가 스레드 수(grace 포함). 상한(#117)을 정할 운영 최대치를 얻는 자리이고, 동시에
**예산이 거절만 하고 종료하지 않은 경우를 밖에서 볼 수 있는 유일한 값**이다 — 응답은 어느 쪽이든 같다.
⚠️ 다시 평가해야 하는 `/readyz` 는 자기 워커를 띄우므로, 그 값은 순간값이다.
