# 정책 평가를 별도 모듈 그래프로 옮긴다 — #89 와 realm 격리를 합친 설계

**상태**: 설계만. 구현은 이 문서가 머지된 뒤 사용자에게 다시 묻는다.
**합치는 근거**: #89(모듈 그래프 누출)의 1안과 realm 격리가 **같은 변경**이다. 따로 하면 두 번 한다.

**범위**: 이 문서는 **셋만** 담는다 — 측정(§1), **하나의 결정**(§2, 경계), 그리고 **구현 전에
정할 것의 목록과 그 재료가 되는 측정**(§3). 대안은 §4 에 열린 채로 둔다.

⚠️ **두 번 줄였고, 두 번 다 같은 이유다.** 첫 판은 블로커 여덟 건(P1 1 · P2 7)을 받았고 대부분이
로직이 아니라 **문서가 만든 주장**에 있었다 — 닫힘 대조, 비용 해석, 롤아웃 주장. 줄인 뒤 §3 이
**요건**을 적었고, 거기서 **구멍이 세 번 연속** 나왔다(§3 머리말에 그 순서가 있다). 그래서 §3 도
**요건에서 결정 목록으로** 줄였다.

이 저장소가 기록한 모양 그대로다: **틀이 커질 때마다 주장할 수 있는 것이 늘고, 그것을 검사하는
표면은 그만큼 자라지 않는다.** 넘긴 항목과 각각에 붙은 리뷰 지적은 **#117** 에 있다.

---

## 0. 한 줄

정책 모듈을 **평가마다 새 `worker_threads` 워커**에서 `import()` 하고, **추출과 직렬화까지 워커
안에서 끝낸 뒤** 결과를 `postMessage` 로 받고 **워커를 종료한다.** 모듈 그래프가 워커와 함께
사라지므로 누출이 끝난다.

## 1. 측정

### 1-a. 기존 두 수는 **서로 다른 측정**이었다

| 출처 | 수 | 무엇을 쟀는가 |
|---|---|---|
| #89 합성 | ≈0.28 MB/평가 | V8 `heapUsed`, 강제 GC 2회 뒤 |
| #89 운영 | ≈4.5 Mi/발행 | `kubectl top` = 컨테이너 working set, 평가 3회 |

4.5 Mi ÷ 3 ≈ **1.5 Mi/평가** 대 **0.28 MB/평가** 는 약 5배다. **#89 는 그 차이를 「`kubectl top`
이 heap 말고 컴파일된 모듈 코드 같은 V8 메모리까지 세기 때문」으로 제안하지만, 그 측정으로
세워지지는 않았다.** 그래서 아래 표는 heap 과 RSS 를 **같은 줄에** 적는다.

⚠️ 앞선 판은 「**#89 에 적혀 있지 않다**」라고 적었다. **적혀 있다** — 내가 읽은 줄이고, 그것을
축소했다. 과장을 피하려다 **원본을 줄인** 자리다.

### 1-b. 로컬 — 픽스처 **A**

**기준**: node 26.4.0 · darwin 25.6.0 · `--expose-gc` · 각 표본은 **강제 GC 2회 + macrotask
yield** 뒤 `process.memoryUsage()` · 평가 **60회** · 2026-10-06.

**픽스처 A 의 모양**: `policies.json` **0.19 MB**(객체 540행, 각 행에 문자열 넷·배열 둘) ·
사이트 모듈 **0.13 MB**(`const` 선언 1,080개 + 그 JSON 을 `import`).

| 조건 | heapUsed/평가 | rss/평가 |
|---|---|---|
| 지금 (자식까지 버전 — #59·#63) | **+0.556 MB** | **+0.626 MB** |
| 자식 버전 훅 OFF (#59 이전 동작) | **+0.343 MB** | +0.346 MB |
| 평가마다 워커, 종료 | **+0.016 MB** | 1-e |

10회마다 표본을 떠서 **선형**이다. 평가가 멈추면 늘지 않고 **줄지도 않는다.**

### 1-c. 로컬 — 픽스처 **B** (같은 표에 섞지 않는다)

**픽스처 B 의 모양**: `policies.json` **0.32 MB**(객체 900행) · 사이트 모듈 **0.08 MB**(`const`
700개). 기준은 1-b 와 같다.

| 조건 | heapUsed/평가 |
|---|---|
| 지금 | **+0.582 MB** |
| 자식 버전 훅 OFF | **+0.229 MB** |

🔑 **A 와 B 를 나눠 적는 이유**: 앞선 판이 **A 의 수와 B 의 수를 한 절에 섞어** 「훅이 2.5배」라고
적었다(그 2.5배는 **B** 의 비, A 는 1.62배다). 픽스처가 다르면 **다른 실험**이고, 비율도 함께
움직인다.

### 1-d. 🔴 #89 의 합성 수는 **재현되지 않았다**

```
#89        0.13 → 0.28  MB/평가   (2.15배)
픽스처 A   0.343 → 0.556 MB/평가  (1.62배)
```

**#89 가 적은 바이트 크기에 맞췄는데도** 2배 차이다.

**가릴 수 없다**: #89 는 픽스처의 **크기만 적고 모양을 적지 않았다.** 바이트 수는 보존되는 heap
을 결정하지 않는다 — 큰 배열 하나와 객체 리터럴 1,080개는 다르게 남는다. ⚠️ 그것이 **차이의
원인이라고는 적지 않는다**(앞선 판은 그렇게 적었다). **왜 다른지 세울 방법이 없다**는 것까지가
세워진 것이다.

→ 재현된 것은 **모양**(선형 · 회수 없음 · 훅이 증폭)이고 **크기는 아니다.** 그래서 이 문서는
자기 픽스처의 **모양**을 §1-b·§1-c 에 적는다.

### 1-e. 워커의 RSS — 한 번 틀리게 적었다

처음 「워커도 RSS +0.543 MB/평가」로 적었다. N 을 바꾸면:

| N | 총 증가 | 「평가당」 |
|---|---|---|
| 15 | +5.34 MB | +0.356 MB |
| 30 | **−5.08 MB** | −0.169 MB |
| 60 | **−1.63 MB** | −0.027 MB |

120회에서는 끝 표본이 10회 때보다 낮았다(63.23 대 64.63 MB).

→ **이 실행들에서 지속적인 RSS 증가는 관측되지 않았다.** ⚠️ 「늘지 않는다」고는 적지 않는다
(앞선 판은 그렇게 적었다). 음수와 N 에 반비례하는 「평가당」 값은 **일회성 비용을 N 으로 나눈
모양과 일치**하지만, **그 설명이 측정된 것은 아니다.**

### 1-f. 운영 대조 — 평가 없으면 평평하다

**기준**: `kubectl top pod --containers` 의 render 컨테이너 working set, 15분 간격. 평가 수는
render 로그의 `evaluated` 줄 누계. **heliopause-ba 측정**, 원본
`/private/tmp/claude-501/audit-d35372c2/render-memory.tsv`(10-05 07:06~14:08Z 행은 무효 표시).

| 관측 | 값 |
|---|---|
| 평가 없는 구간 | 파드 `n7mf4` 약 **71시간** 35~36 Mi · 파드 `2drcp` 약 **9시간** 30~31 Mi |
| 계단 | +3평가 → **+4~5 Mi** · +3평가 → **≈0** · +4평가 → **+3~4 Mi** |
| 누적을 지운 것 | **롤아웃(파드 교체)만** — 39 → 30 Mi |

⚠️ **그 쪽이 명시한 한계**: `≈0` 계단이 GC 회수인지 **1 Mi 해상도에 묻힌 것인지 가를 수 없다.**
계단은 **발행 수가 아니라 평가 수**를 따른다. 표본 사이 공백이 셋.

🔑 로컬 `+0.626 MB/평가`(픽스처 A, RSS)와 운영 `≈1~1.5 Mi/평가` 는 **같은 자릿수다. 같다고는
적지 않는다** — **로컬 RSS 와 컨테이너 working set 은 다른 대상**이다.

### 1-g. 원인 — ESM 레지스트리이고, 자식 버전 훅은 **증폭기**다

`import("<site>?v=<stamp>")`(`bin/heliopause-policy-render.ts:819`)의 URL 이 스탬프마다 바뀐다.
**ES 모듈은 URL 로 캐시되고, 프로세스가 항목을 지울 수 없다.**

| 대조군 | 결과 | 무엇을 배제하는가 |
|---|---|---|
| 결과를 **아예 버린다**(`held = null`) | 수가 **동일**(소수점까지) | **명시적으로 들고 있던 export** 가 원인이 아니다. ⚠️ 「이 프로세스가 들고 있는 것이 아니다」라고는 적지 않는다 — **ESM 레지스트리도 이 프로세스 안**이다 |
| 자식 버전 훅 **OFF** | 줄지만 **0 이 아니다** | 훅(`:486`)은 **원인이 아니라 증폭기**다. entry 모듈만 버전해도 레코드가 남는다 |

`cached.set(sitePath, …)`(`:893`)은 슬롯 하나이고 이전 `source` 는 풀린다.

ℓ **Node 에 레코드를 evict 하는 공개 API 를 나는 모른다.** 「없다」고 적지 않는다 — 찾아본 범위가
그만큼이다.

### 1-h. 비용

**기준**: 타임드 루프 **안에 GC 없음**, 첫 회를 따로 적음, 20회 평균, node 26.4.0.
**측정한 것은 `import()` 와 작은 응답 하나의 왕복이다** — **완전한 `PolicySource` 를 만들고
복제하는 비용은 재지 않았다**(§2 가 그것을 워커로 옮기므로 구현 때 다시 재야 한다).

```
워커        첫 41.7 ms · 그 뒤 17.9 ms/평가
인프로세스  첫  2.2 ms · 그 뒤  1.7 ms/평가
```

⚠️ 이 수가 **어느 요청 경로에 어떻게 붙는지는 이 문서가 주장하지 않는다.** 평가는 **기동**,
**`/readyz`**, **`/source`** 세 자리에서 일어나고, 앞선 판이 「요청이 올 때만」·「기동은 직렬
합계」라고 적어 둘 다 틀렸다. → **#117**.

## 2. 경계 — **추출과 직렬화는 워커 쪽 필수**

| 일 | 어디서 | 왜 |
|---|---|---|
| `import()` 와 사이트 모듈 평가 | **워커** | 이 설계의 전부 |
| `collectPolicySource`(`resolveService` 호출 + `toWire`) | **워커 (필수)** | 아래 |
| 스탬프(`sourceStamp`) | 부모 | 디스크를 읽을 뿐 모듈을 평가하지 않는다 |

### 왜 **필수**인가 — 함수 값은 추출 **뒤에만** 사라진다

```
src/policy-source.ts:365   const hit = resolver(ref);                              ← resolveService 호출
src/policy-source.ts:376   if (hit) services[ref] = toWire(hit) as ServiceSelector;
src/policy-source.ts:409   const wire = toWire({ ...site, resolveService: undefined }) as ScreenSite;
```

### 불변식은 **어디서부터 참인가**

| 자리 | 그 시점의 값 | 클론 가능한가 |
|---|---|---|
| `src/policy-source.ts:365` **전** — 원시 `site` | `resolveService` **함수**를 들고 있다 | ❌ |
| `:376` · `:409` **후** — `site` 와 `services` | `toWire`(JSON 왕복, `:53-54` 의 캡처된 `parseJson`/`writeJson`)를 지났다 | ✅ |
| `:437` — `repo.probes` | `readCoverageProbes` 가 **그대로** 넣는다. **`toWire` 를 지나지 않는다** | ❌ **보장 없음** |

🔴 **그래서 「`PolicySource` 에는 JSON 으로 표현되는 값만 남는다」는 거짓이다.** `toWire` 는
**`site` 와 resolver 결과만** 덮고, 완전한 source 는 **그 뒤에 조립된다.** `repo.probes` 는
`src/policy-screen.ts:146` 의 **캡처되지 않은 `JSON.parse`** 가 돌려준 것을 직렬화 없이 싣는다 —
독립 리뷰가 그 파서를 함수를 품은 probe 를 돌려주는 것으로 갈아치우니 `collectPolicySource` 는
**성공하고** 그다음 `structuredClone(source)` 이 **`DataCloneError`** 로 던졌다.

⚠️ 같은 문장을 **두 번 연속 한 방향으로만 참**이게 적었다. 처음엔 「함수 값은 이미 넘지 않는다」
(P1 블로커), 고치면서 「`:409` 이후에만 참」 — **그 뒤에 또 조립되는 자리를 못 봤다.**

### 요건

1. **워커가 나가는 `PolicySource` 전체를 자기 안에서 직렬화한다 — `repo.probes` 를 포함해서.**
   부모는 **직렬화된 바이트만** 받는다. 「어디까지 `toWire` 를 지났는가」를 따지는 설계는 위 표가
   보여준 자리에서 또 틀린다.
2. **직렬화나 클론이 실패하면 그 사이트의 실패로 처리한다**(503). 워커를 종료하고, 캐시에 넣지
   않는다.

ℓ **실제 `PolicySource` 를 워커로 보내 보지 않았다.** 근거는 위 표의 코드 줄과 리뷰의 프로브다.
**구현의 첫 작업이 그것을 보내는 테스트**여야 한다.

### 존 검사의 자리는 정하지 않는다

`zoneMismatch` 를 부모에 두면 **와이어 데이터**를 검사하므로 모듈이 위조할 수 없고, 워커에 두면
한 번에 끝난다. **정하지 않았다** → **#117**.

## 3. 워커 생애주기 — **구현 전에 정할 것**

⚠️ **이 절은 요건을 적지 않는다.** 앞선 세 판이 여기에 규칙을 적었고, **세 번 연속 그 규칙 안에서
구멍이 나왔다**:

```
2라운드  「먼저 온 것이 이긴다」            → 모듈이 parentPort 로 위조를 먼저 보낸다
그 수정   전용 포트를 workerData 로 넘긴다  → 모듈이 workerData.reply 를 읽어서 보낸다
3라운드  초기 메시지로 넘긴다              → import 를 먼저 하면 모듈이 포트를 훔친다
그 수정   순서를 지킨다                    → prototype 메서드를 갈면 포트 없이도 보낸다
```

**셋 다 내가 쓴 요건에서 나왔다.** 규칙을 쓰면 그 규칙에 대한 주장이 공짜로 생기고, 그 주장이
검사되지 않는다 — 이 저장소가 「일반적인 장치는 완전하다는 주장을 공짜로 만든다」로 기록한 그
자리다. 그래서 **정해야 할 것만 적고, 답은 적지 않는다.** 아래 §3-b 의 측정이 그 결정의 재료다.

### 3-a. 결정해야 할 것

평가 하나는 **정확히 한 번 결말**이 나야 하고 **모든 결말에서 워커가 종료**돼야 한다. 그러지
않으면 이 설계가 고치려는 누출이 **스레드 누출로 바뀐다.** 그 둘을 어떻게 보장하는지가 결정이다.

| 정해야 할 것 | 왜 자명하지 않은가 |
|---|---|
| 어떤 신호를 **결과**로 받는가 | 「메시지가 왔다」는 성공이 아니다 — §3-b ① |
| 결과가 **어느 채널**로 오는가 | 전용 채널만으로는 부족하다 — §3-b ② |
| 평가기가 그 채널을 **언제** 잡는가 | 순서가 결과를 바꾼다 — §3-b ② |
| 평가기가 **보내는 함수**를 어떻게 부르는가 | 호출 시점 lookup 이 갈린다 — §3-b ③ |
| `message`·`error`·`exit` 가 **함께** 올 때 | 결말이 둘이 되면 안 된다 |
| 결과 **없이** 끝나는 길 | 모듈의 `process.exit(0)` 은 `message` 도 `error` 도 안 남긴다 — §3-b ④ |
| 직렬화·클론 실패 | §2 가 「그 사이트의 503」으로 정했다. 워커 종료와 캐시 금지가 따라온다 |
| 평가 타임아웃·동기 spin | 아무 이벤트도 안 온다. 부모 타이머가 `terminate()` 한다(§4 가 그것을 쟀다) |
| **동시에 뜨는 워커 수** | `resourceLimits` 는 **그 워커의 힙**에 걸리고 컨테이너 한도는 **프로세스 전체**에 걸린다. 합이 넘을 수 있다 → **#117** |
| 지연된 결함의 **가시성** | 종료가 모듈의 늦은 throw 를 삼킨다. 로그·`faults` 집계가 어떻게 바뀌는지 → **#117** |

#### 🔑 2026-10-07 — 결말에 대한 셋이 **정해졌다**

사용자 결정. 위 표의 세 줄(「어떤 신호를 결과로」·「셋이 함께 올 때」·「결과 없이 끝나는 길」)이
닫힌다. 나머지 일곱은 열려 있다.

| 결정 | 정해진 것 |
|---|---|
| **결과로 받는 것** | **전용 채널 + 스키마 통과 + 문자열(바이트)** 만. 다른 경로·다른 모양은 결과가 아니다 |
| **셋이 함께 올 때** | **검증을 통과한 첫 결과를 즉시 채택해 응답**한다. 워커는 **상한 있는 짧은 grace 동안 살려 둔다** — 그사이 오는 `error`·비정상 `exit` 는 **`faults` 로 세고 로그만** 남기고 **응답도 캐시도 바꾸지 않는다.** grace 를 넘기면 `terminate()` |
| **결과 없는 `exit`** | **그 사이트 503 + 캐시 금지** — §2 의 직렬화 실패와 같은 처리 |

바이트로 정한 것은 **#124 가 이미 `Promise<string>`** 이기 때문이다. 객체를 받으면 §10·§11 이
기록한 `then`·`toJSON` 질문이 **워커 경계에서 다시 생긴다.**

🔑 **grace 가 있는 이유: 그것이 오늘 렌더러의 동작이다.** 모듈이 올바른 결과를 준 뒤 비동기로
터지면 지금은 `uncaughtException`·`unhandledRejection` 핸들러가 **`faults` 를 올리고 로그를 남기며
서빙은 유지한다**(`bin/heliopause-policy-render.ts:163-170`, 그리고 `lateThrowFromModuleTimer`
shape 이 `faults > 0` 을 단언한다). 결과를 받고 **곧바로 종료**하면 그 가시성이 **사라진다** — 즉
워커 이전이 **현재 있는 신호를 잃는 변화**가 된다. grace 는 그것을 **옮겨 오는** 장치다.

⚠️ **이 문단은 처음에 정확히 반대로 적혀 있었다** — 「지금도 조용하다, 바뀌는 것은 원인이고 증상은
같다」. 독립 리뷰가 그 핸들러를 읽어 반증했고, 그 **틀린 서술이 결정의 대가를 가린 채 사용자에게
전달됐다.** 그래서 결정이 한 번 뒤집혔다. **「지금 코드가 무엇을 하는가」를 소스에서 확인하지 않고
대가를 적으면, 그 대가를 근거로 내린 결정이 틀린다.**

##### grace 값 — 제안과 그 한계

🔴 **어떤 grace 도 늦은 결함을 전부 잡지 못한다.** 모듈은 타이머를 **임의로 길게** 걸 수 있다.
§3-b ④ 가 그 경계를 쟀다 — 모듈이 200 ms 타이머를 걸었을 때 **50 ms 에 종료하면 `error` 가 오지
않고**, **600 ms 살려 두면 온다.** 그러므로 grace 는 **「무엇을 잡는가」가 아니라 「얼마를 내는가」**
로 정해야 한다.

가진 수로 제안한다:

| 들어가는 수 | 값 |
|---|---|
| 워커 평가 비용(§1-h) | 첫 **41.7 ms** · 그 뒤 **17.9 ms**/평가 |
| 관측된 늦은 throw 창(§3-b ④) | 200 ms 타이머가 **600 ms** 안에 도착 |
| 평가 빈도 | 스탬프가 움직일 때만 — **발행 단위**이고 요청 단위가 아니다 |
| 동시 워커 상한 | **#117** — `resourceLimits` 는 워커 힙에, 컨테이너 한도는 프로세스 전체에 걸린다 |

→ **제안: grace 1,000 ms.** 관측된 600 ms 를 덮고, 평가가 발행 단위라 **상시 비용이 아니다.**
grace 중의 워커는 **동시 워커 상한에 계속 센다** — 그 상한이 #117 에서 정해져야 이 값이 안전한지
말할 수 있고, **그래서 이 제안은 #117 에 걸려 있다.**

⚠️ **1,000 ms 는 측정이 아니라 선택이다.** 측정된 것은 **600 ms 안에 그 특정 타이머가 도착했다**는
것 하나뿐이고, 「1,000 ms 면 대부분 잡는다」는 **재지 않았다.** 분포를 모른다 — 관측은 **한 건**이다.

⚠️ 그리고 **「곧바로 응답」과 「grace」는 서로 다른 시계다.** 응답은 첫 유효 결과에서 바로 나가므로
grace 는 **응답 지연에 들어가지 않는다.** grace 가 미루는 것은 **워커 회수**이고, 그래서 비용이
나타나는 자리는 **지연이 아니라 동시 워커 수와 메모리**다 — 다시 #117 이다.

ℓ **grace 가 막지 못하는 것도 적어 둔다**: 모듈이 **올바른 결과를 보낸 뒤 그 값이 틀렸다는 것**은
어떤 grace 로도 안 보인다. 그것은 스키마 검증이 보는 것이고, §3-b ⑤ 가 **그 검증이 `probes`
내용물에는 돌지 않는다**고 적는다. #126 이 정확히 그 자리에서 났다.

### 3-b. 측정 기록

**전부 2026-10-06, node 26.4.0, darwin 25.6.0.** 스크립트는 §6 에 있다. 아래는 **관측**이고
요건이 아니다 — 읽는 쪽이 설계를 정할 때 쓰는 재료다.

#### ① 정책 모듈이 `parentPort` 로 **먼저 답한다**

모듈이 `import { parentPort } from "node:worker_threads"` 를 **자기가** 하고 `postMessage` 를
부른 뒤 throw 했다. 부모가 받은 순서:

```
  message: {"hosts":[{"id":"forged.by-the-module","stage":"gateway"}]}
  error: the real evaluation then failed
  exit: 1
```

→ **메시지가 먼저 온다.** 「먼저 온 것을 결과로 받는다」와 「메시지 = 정상」이 만나면 부모가
**위조를 받고 실제 실패를 버린다.**
(`forge.mjs` · `forge-child.mjs`)

#### ② 전용 `MessageChannel` 포트 — **넘기는 방법과 순서가 결과를 바꾼다**

부모가 `MessageChannel` 을 만들어 워커에 넘기고, 모듈이 세 방향으로 답하려 했다.

| 포트를 넘기는 방법 | 위조가 **전용 포트**에 도착하는가 |
|---|---|
| `workerData` 에 넣는다 | 🔴 **도착한다** — 모듈이 `workerData.reply` 를 **읽어서** 보낸다 |
| 초기 `postMessage`, 평가기가 **`import` 전에** 받는다 | **도착하지 않는다** |
| 초기 메시지인데 평가기가 **`import` 를 먼저** 한다 | 🔴 **도착한다** — 모듈이 `parentPort.once("message")` 로 **포트를 훔치고**, 평가기는 포트를 잃는다 |

세 실행 **모두에서** 위조가 `parentPort` 에는 도착했다 — 모듈이 그것을 import 할 수 있으므로
**막을 수 없다.**

평가기가 그 포트를 **전역에 두거나 export 하면 다시 열린다.** 내 평가기는 두지 않았고 모듈이
읽으려 한 `globalThis.__evaluatorReplyPort` 는 **absent** 로 측정됐다.
(`port-test.mjs` · `port-child.mjs` · `steal-test.mjs` · `steal-child.mjs`)

#### ③ 포트에 닿지 못해도 **보내는 메서드**를 갈면 된다

모듈이 포트 객체를 전혀 보지 못하는 설정에서, `MessagePort.prototype.postMessage` 를 갈아치웠다.

| 평가기가 보내는 방법 | 위조가 부모에 도착하는가 |
|---|---|
| `reply.postMessage(payload)` — **호출 시점**에 메서드를 찾는다 | 🔴 **도착한다** |
| `MessagePort.prototype.postMessage` 를 **첫 import 전에 캡처**해 `.call(reply, payload)` | **도착하지 않는다** |

모듈이 쓴 코드는 두 줄이다:

```js
const original = MessagePort.prototype.postMessage;
MessagePort.prototype.postMessage = function (v, ...r) { return original.call(this, forged, ...r); };
```

🔑 **이 저장소가 이미 기록한 모양이다.** `bin/heliopause-policy-render.ts:120` 의 주석이 똑같이
적는다 — 「**집합은 모듈이 닿을 수 없었지만 *lookup* 은 닿을 수 있었다**」. 거기서는
`WeakSet.prototype.has` 였고 여기서는 `MessagePort.prototype.postMessage` 다.

⚠️ **그래서 「모듈이 다른 모듈의 스코프에 닿는 길」은 물을 필요도 없었다.** 공유 prototype 으로
충분했다. **다른 공유 표면이 또 있는지는 재지 않았다** — `receiveMessageOnPort`,
`EventEmitter.prototype.once`, `structuredClone` 자체. **구현 전에 재야 할 것.**
(`proto-test.mjs` · `proto-child.mjs`)

#### ④ 결과 없이 끝나는 길

모듈이 `process.exit(0)` 을 부르면 **`message` 도 `error` 도 오지 않는다.** `exit` 이벤트만 남는다.

늦은 throw 는 종료 시점에 달렸다: 50 ms 에 종료하면 `error` 가 **오지 않고**(결과는 전달됨),
600 ms 살려 두면 모듈의 200 ms 타이머가 발사돼 **`error` 가 부모에 워커 `error` 이벤트로 도착**
하며 프로세스는 살았다.
(`six-rows.mjs`)

#### ⑤ 스키마 검증은 **이미 있다** — `probes` 내용물에는 돌지 않는다

`parsePolicySource`(`src/policy-source.ts:186`)가 와이어를 검사한다: `repo.probes` 가 배열인지
(`:264`), 그리고 **`site` 의 어느 키도 함수가 아닌지**(`:255-257`).

```
for (const [k, val] of Object.entries(s)) {
  if (typeof val === "function") bad(`site.${k} is a function — this boundary carries data only`);
}
```

⚠️ **그 함수 검사는 `site` 의 자기 키들에 대한 것이고 `probes` 의 내용물에는 돌지 않는다.** §2 의
요건 1(나가는 `PolicySource` **전체**를 워커 안에서 직렬화)이 필요한 또 하나의 이유다.

### 3-c. 격리는 더 좁아진다

**측정**(같은 기준): 부모에 비밀을 심고 워커가 보는 env 를 셌다.

|---|---|---|

→ #89 의 「worker 는 기본적으로 부모의 env 를 복사한다」는 맞다. **`env: {}` 로 지금보다 좁게**
만들 수 있다. 평가에 실제로 필요한 env 는 **구현 시 측정해서 정한다.**

## 4. 대안 — `vm` 은 **열린 선택지**다

| | 동기 spin | 메모 |
|---|---|---|
| `worker_threads` | **끊는다** — `terminate()` 가 `exitCode=1`, 부모 이벤트 루프는 막히지 않았다 | §3 의 생애주기가 필요하다 |
| **`vm`** | **끊는다** — `ERR_SCRIPT_EXECUTION_TIMEOUT`, **303 ms**, 메인 스레드 생존. `vm.Script` 와 `vm.SourceTextModule.evaluate({timeout})` **둘 다** | ⚠️ **`vm.SourceTextModule` 은 실험 기능**(`--experimental-vm-modules`) |

⚠️ **앞선 판은 `vm` 을 「같은 스레드라 동기 spin 을 못 닫는다」로 기각했다. 그것은 거짓이고, 내가
보탠 문장이다** — AGENTS.md 는 `vm` 을 **선택지로** 적는다. 기각한 대안을 틀린 근거로 기각하면
읽는 쪽이 그 선택지를 **다시 보지 않는다.** 그래서 열어 둔다.

### 4-a. 🔴 그 빈칸을 쟀다 — **`vm` 은 메모리를 풀지 않는다**

위 문단은 오래 「**메모리가 실제로 풀리는지** — `vm` 쪽은 재지 않았다」로 끝나 있었다. 쟀다.

**기준**: node 26.4.0 · darwin 25.6.0 · `--expose-gc --experimental-vm-modules` · 표본마다 강제 GC
2회 + macrotask yield · **픽스처 A**(§1-b — `policies.json` 0.19 MB 객체 540행 + 선언 1,080개짜리
모듈 0.13 MB) · 40회 · 2026-10-07 · `scripts/measure-realm-memory.mjs`.

| 조건 | heapUsed/평가 | rss/평가 | 40회 총 heap |
|---|---|---|---|
| **current-hook-on** — 오늘 렌더러(자식까지 버전) | **+0.559 MB** | +0.840 MB | 22.34 MB |
| current-hook-off — #59 이전 동작 | +0.339 MB | +0.420 MB | 13.57 MB |
| **worker** — 평가마다 워커, `terminate()` | **+0.007 MB** | +0.371 MB | **0.29 MB** |
| `vm-script` — `vm.Script`, JSON **인라인** | +0.638 MB | +0.758 MB | 25.54 MB |
| **`vm-module`** — `vm.SourceTextModule` | **+0.579 MB** | +0.522 MB | 23.15 MB |

위 두 행이 **§1-b 를 재현한다**(그 표의 0.556 · 0.343). 같은 픽스처·같은 절차이고, 그래서 아래
`vm` 행들을 **오늘 렌더러와 같은 자 위에서** 읽을 수 있다.

🔴 **그러므로 결론은 이것이다: `worker` 가 `vm` 보다 heapUsed 기준 약 80배 적다**(0.007 대 0.579).
`vm` 은 **오늘 렌더러와 사실상 같다**(0.579 대 0.559) — **#89 의 누출을 줄이지 않는다.**

⚠️ **「`vm` 은 지금보다 더 쓴다」라고 적었고 그것은 틀렸다.** 그때 `current` 로 적은 0.347 은
**자식 버전 훅을 설치하지 않은** 측정이어서 **#59 이전 동작**(0.339)이었고, 오늘 렌더러가 아니었다.
독립 리뷰가 스크립트를 읽어 그 조건을 집었다. 고친 뒤 `vm` 은 「더 쓴다」가 아니라 **「같다」**다.

🔑 **그래서 비교 대상을 잘못 고르면 결론이 과장되는 쪽으로 틀린다.** 이 파일이 「**무엇에 대고
쟀는지 같은 줄에 적어야 한다**」고 적어 둔 그 자리이고, 이번에는 **행 이름이 그 역할을 했어야**
했다 — `current` 라는 이름이 **묻지 않게** 만들었다. 지금은 두 행이 각각 `-hook-on`·`-hook-off` 다.

⚠️ **훅이 실제로 발사됐는지 세야 한다.** 고친 첫 판에서 두 행이 **0.008 MB 차이**로 나왔고, 그것은
「훅이 공짜다」가 아니라 **「훅이 한 번도 안 돌았다」**였다. 원인은 **ESM 해석이 모듈 URL 을
realpath 로 바꾸는 것**이다 — macOS 에서 `mkdtempSync` 는 `/var/folders/…` 를 주는데 자식 specifier
는 `/private/var/folders/…` 로 풀려 루트 검사가 **매번 실패**했다. 스크립트는 이제 **버전을 매긴
자식 specifier 수를 함께 인쇄한다**(위 표의 조건에서 **40 = 평가당 1**, 그 픽스처의 JSON import).

### 4-b. 무엇이 남는지 — 대조군 셋

「내 루프가 들고 있는 것 아닌가」를 먼저 갈라야 한다. 같은 `vm-module` 평가를 돌리며 한 번에
하나씩 뺐다(60회, `scripts/measure-realm-memory.mjs --retention 60`):

| | 60회 총 heap | /iter |
|---|---|---|
| 모듈 평가 + **namespace 보유** | +34.91 MB | 0.582 |
| 모듈 평가 + **아무것도 안 들기** | **+34.13 MB** | **0.569** |
| **컨텍스트만** 만들고 버리기(모듈 없음) | **+0.00 MB** | **0.000** |

→ **아무것도 들고 있지 않아도 거의 그대로 남는다**(0.569 대 0.582 — 차이 0.013). 즉 **잔류는 참조를
들고 있어서 생기는 것이 아니다.** 그리고 **컨텍스트만 만들고 버리면 0.000** 이다.

⚠️ **세운 범위는 「컨텍스트만 만들 때보다 모듈 평가 경로에서 잔류가 늘어난다」까지다.** 처음에
「컨텍스트가 아니라 **모듈 그래프**가 남는다」로 적었고, 그것은 이 대조군이 세우지 못한다 — **모듈
평가가 컨텍스트까지 함께 붙잡는 경우**를 배제하지 않았다(독립 리뷰가 지적했다). 무엇이 남는지
가리려면 heap 스냅샷의 retainer 를 봐야 하고, 그건 이 측정에 없다.

⚠️ 그리고 **첫 판의 이 표는 커밋한 스크립트가 낸 것이 아니었다**(27.29 / 26.32 / 0.16). 그 수는
스크래치패드의 별 스크립트가 냈고, 커밋한 쪽은 `vm-module` 이 **숫자를 반환**해서 「namespace 보유」
대조군이 **숫자를 들고 있었다** — 두 대조군이 다 아무것도 안 들었으니 **가르려던 것을 가르지
않았다.** §7 은 그 스크립트가 이 표를 낸다고 적고 있었다. 독립 리뷰가 돌려 보고 집었다.

### 4-c. 그래서 §4 는 닫힌다 — 다만 **이 배치에 대해서만**

**`worker_threads` 가 유일한 측정된 선택지다.** `vm` 보다 **약 80배** 적다.
