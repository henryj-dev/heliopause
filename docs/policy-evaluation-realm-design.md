# 정책 평가를 별도 모듈 그래프로 옮긴다 — #89 와 realm 격리를 합친 설계

**상태**: 설계만. 구현은 이 문서가 머지된 뒤 사용자에게 다시 묻는다.
**합치는 근거**: #89(모듈 그래프 누출)의 1안과 realm 격리가 **같은 변경**이다. 따로 하면 두 번 한다.

이 문서는 **측정된 것과 측정하지 않은 것을 줄마다 가른다.** 이 저장소가 기록한 반복 결함이
「코드는 움직였고 그것을 설명하는 문장은 더 멀리 움직였다」이고, 설계 문서는 그 문장을 가장 많이
담는 자리다.

---

## 0. 한 줄

정책 모듈을 **평가마다 새 `worker_threads` 워커**에서 `import()` 하고, 결과를 `postMessage` 로
받은 뒤 **워커를 종료한다.** 모듈 그래프가 워커와 함께 사라지므로 누출이 끝나고, 같은 realm 에서
닫을 수 없다고 기록된 구멍 몇 개가 함께 닫힌다.

## 1. 무엇이 남는가 — 측정

### 1-a. 두 기존 수는 **서로 다른 측정**이었다

| 출처 | 수 | 무엇을 쟀는가 |
|---|---|---|
| #89 합성 | ≈0.28 MB/평가 | V8 `heapUsed`, 강제 GC 2회 뒤 |
| #89 운영 | ≈4.5 Mi/발행 | `kubectl top` = 컨테이너 working set(RSS 계열), 평가 3회 |

4.5 Mi ÷ 3 ≈ **1.5 Mi/평가** 대 **0.28 MB/평가** 는 약 5배다. **그 차이가 측정 기준 때문인지
실제인지 이슈에 적혀 있지 않다.** 그래서 아래 재현은 heap 과 RSS 를 **같은 줄에** 적는다.

### 1-b. 로컬 재현

**측정 기준(모든 행 공통)**: `node --expose-gc`, 각 표본은 **강제 GC 2회 + macrotask yield** 뒤
`process.memoryUsage()`. 픽스처는 `policies.json` **0.19 MB** · 사이트 모듈 **0.13 MB**(바이트를
재서 #89 가 적은 크기에 맞춤), 사이트 모듈이 그 JSON 을 `import` 한다. 평가 **60회**.
**node 26.4.0, darwin 25.6.0.** 2026-10-06.

| 조건 | heapUsed/평가 | rss/평가 |
|---|---|---|
| **지금** (자식까지 버전 — #59·#63) | **+0.556 MB** | **+0.626 MB** |
| 자식 버전 훅 OFF (#59 이전 동작) | **+0.343 MB** | +0.346 MB |
| **평가마다 워커, 종료** | **+0.016 MB** | **늘지 않음** (1-e) |

10회마다 표본을 떠서 **선형**이다. 평가가 멈추면 늘지 않고 **줄지도 않는다.**

### 1-c. 🔴 제 크기는 #89 의 **2배**이고, 그 차이를 세울 수 없다

```
#89     0.13 → 0.28  MB/평가   (2.15배)
이 문서 0.343 → 0.556 MB/평가  (1.62배)
```

**같은 바이트 크기로 맞췄는데도** 그렇다. 원인은 **#89 가 픽스처의 크기만 적고 모양을 적지
않았다**는 것이다. 이 문서의 픽스처는 객체 540행 JSON + `const` 선언 1,080개이고, #89 의 것이
무엇이었는지는 알 수 없다. **바이트 수는 보존되는 heap 을 결정하지 않는다** — 큰 배열 하나와
객체 리터럴 1,080개는 다르게 남는다.

→ **#89 의 합성 수는 #89 만 보고 재현할 수 없다.** 재현된 것은 **모양**(선형 · 회수 없음 ·
훅이 약 2배)이고 **크기는 아니다.** 그래서 이 문서는 자기 픽스처의 **모양**을 위에 적는다.

### 1-d. 운영 대조 — 평가 없으면 평평하다

**측정 기준**: `kubectl top pod --containers` 의 render 컨테이너 working set, 15분 간격.
평가 수는 render 로그의 `evaluated` 줄 누계. heliopause-ba 측정, 원본
`/private/tmp/claude-501/audit-d35372c2/render-memory.tsv`(10-05 07:06~14:08Z 행은 무효 표시).

| 관측 | 값 |
|---|---|
| 평가 없는 구간 | 파드 `n7mf4` 약 **71시간** 동안 35~36 Mi · 파드 `2drcp` 약 **9시간** 동안 30~31 Mi |
| 계단 | +3평가 → **+4~5 Mi** · +3평가 → **≈0** · +4평가 → **+3~4 Mi** |
| 누적을 지운 것 | **롤아웃(파드 교체)만** — 39 → 30 Mi |

⚠️ **그 쪽이 명시한 한계**: `≈0` 계단이 GC 회수인지 **1 Mi 해상도에 묻힌 것인지 가를 수 없다.**
계단은 **발행 수가 아니라 평가 수**를 따른다(`/source` 호출 때만 평가한다). 표본 사이 공백이 셋.

🔑 **로컬 `+0.626 MB/평가` 와 운영 `≈1~1.5 Mi/평가` 는 같은 자릿수다. 같다고는 적지 않는다** —
**로컬 RSS 와 컨테이너 working set 은 다른 대상**이다. 나란히 두는 것이 이 표의 용도다.

### 1-e. ⚠️ 워커의 RSS 를 한 번 틀리게 적었다 — **일정값을 N 으로 나눈 것**

처음 「워커도 RSS 는 +0.543 MB/평가」로 적었다. N 을 바꿔 보니 서명이 드러났다:

| N | 총 증가 | 「평가당」 |
|---|---|---|
| 15 | +5.34 MB | +0.356 MB |
| 30 | **−5.08 MB** | −0.169 MB |
| 60 | **−1.63 MB** | −0.027 MB |

120회에서는 **끝 표본이 10회 때보다 낮았다**(63.23 대 64.63 MB). → **워커는 RSS 를 늘리지
않는다.** 처음 수는 **워커 기반을 처음 띄우는 일회성 비용**을 평가 수로 흩뿌린 것이다. 표를 읽어
잡았고, 이 저장소가 「설정 변경을 가로질러 수를 옮기지 말라」로 적어 둔 모양이다.

## 2. 원인 — ESM 레지스트리이고, 자식 버전 훅은 **증폭기**다

`import("<site>?v=<stamp>")`(`bin/heliopause-policy-render.ts:819`)의 URL 이 스탬프마다 바뀐다.
**ES 모듈은 URL 로 캐시되고, 프로세스가 항목을 지울 수 없다.**

대조군 둘로 갈랐다:

| 대조군 | 결과 | 무엇을 배제하는가 |
|---|---|---|
| 결과를 **아예 버린다**(`held = null`) | 수가 **동일**(0.582 / 0.229, 소수점까지) | **이 프로세스가 들고 있는 것이 아니다.** `cached.set(sitePath, …)`(`:893`)은 슬롯 하나이고 이전 `source` 는 풀린다 |
| 자식 버전 훅 **OFF** | 2.5배 줄지만 **0 이 아니다** | 훅(`:486-498`)은 **원인이 아니라 증폭기**다. entry 모듈만 버전해도 레코드가 남는다 |

훅이 자식 JSON·하위 모듈에 같은 `?v=` 를 붙이므로(#59·#63 이 고친 것), 스탬프가 한 번 움직이면
**그래프 전체**가 새 레코드로 들어온다.

ℓ **Node 에 레코드를 evict 하는 공개 API 를 나는 모른다.** 「없다」고 적지 않는다 — 찾아본 범위가
그만큼이다.

## 3. 경계 — **함수 값은 이미 넘지 않는다**

#89 는 `resolveService` 를 걱정했는데, **`buildPolicySource` 가 이미 처리한다**:

```
src/policy-source.ts:362-364   resolveService 를 **즉시 호출**해 services 테이블로 평탄화
src/policy-source.ts:409       toWire({ ...site, resolveService: undefined })
```

`toWire` 는 JSON 왕복이므로(`:53-54` 의 캡처된 `parseJson`/`writeJson`) **`PolicySource` 에는
JSON 으로 표현되는 값만 남는다.** `postMessage` 의 structured clone 은 그것을 받는다.

⚠️ **실제 `PolicySource` 를 워커로 보내 보지 않았다.** 근거는 위 두 줄의 코드다. 구현의 첫 작업이
그것을 보내는 테스트여야 한다.

### 3-a. 어디서 무엇을 돌리는가 — 결정이 필요한 자리

| 일 | 워커 | 부모 | 메모 |
|---|---|---|---|
| `import()` 와 사이트 모듈 평가 | ✅ | | 이 설계의 전부 |
| `buildPolicySource`(`toWire` 포함) | ? | ? | 워커에 두면 직렬화 실패가 **그 사이트만** 죽인다 |
| 존 검사(`zoneMismatch`) | ? | ? | 부모에 두면 **와이어 데이터**를 검사하므로 모듈이 위조할 수 없다 |
| 스탬프(`sourceStamp`) | | ✅ | 디스크를 읽을 뿐 모듈을 평가하지 않는다 |
| 평가 타임아웃 | | ✅ | `terminate()` 가 타이머를 대신한다(§4 행 4) |

**`buildPolicySource` 와 존 검사의 자리는 이 문서가 정하지 않는다** — 사용자 결정이다.
§5 의 캡처 표가 그 선택에 달려 있다.

## 4. 11차 표의 여섯 줄 — 각각 닫히는가

AGENTS.md 「전역 교체는 realm 공유의 **한 가지 방법**일 뿐이다」의 여섯 줄. 추론하지 않고 **각각
돌렸다**(측정 기준: node 26.4.0, 워커 하나를 띄워 결과를 받고 종료, 2026-10-06).

| # | 정책 모듈이 한 일 | 닫히는가 | 측정된 것 |
|---|---|---|---|
| 1 | `resolveService` 가 순환 참조·`BigInt` 반환 | **부분** | 재지 않았다. `toWire` 가 워커에 있으면 그 사이트만 죽는다 — §3-a 의 결정에 달렸다 |
| 2 | `Object.prototype.toJSON` 을 throw 하게 | **부분** | 재지 않았다. 1번과 같은 조건 |
| 3 | `Object.prototype.then` getter 를 throw 하게 | **✅ 닫힌다** | 워커는 `exit 0`, 결과가 전달됐고, **부모의 `Object.prototype.then` 은 그대로 없었다** |
| 4 | 최상단 `while (true) {}` | **✅ 닫힌다** | 부모 타이머가 먼저 발사되고, `terminate()` 가 `exitCode=1` 로 끝났으며, **부모 이벤트 루프가 막히지 않았다** |
| 5 | 모듈의 `setTimeout` 콜백이 나중에 throw | **✅ 닫힌다 — 조건부** | 50ms 에 종료: `error=null`, 결과 전달. 600ms 살려 둠: **`error` 가 부모에 워커 `error` 이벤트로 도착**하고 프로세스는 살았다 |
| 6 | 목록 밖 `./helper.ts` 만 깨뜨리기 | **❌ 안 닫힌다** | realm 과 무관하다 — **스탬프 범위** 문제다(`sourceStamp` 가 보는 트리). 그대로 열려 있다 |

### 🔑 3번과 5번에서 **동작이 바뀐다** — 좋은 쪽이지만 바뀐다

- **3번**: 지금은 **프로세스 exit 1** 이다. 워커에서는 **그 사이트가 정상 응답한다**(`exit 0`,
  결과 전달). `postMessage` 가 `.then` 을 읽지 않기 때문이다. **장애가 아니라 통과로 바뀐다.**
- **5번**: `error` 가 **워커 `error` 이벤트**로 온다. **부모가 그 핸들러를 달지 않으면** 부모의
  uncaught exception 이 된다. 그래서 이것은 **공짜가 아니라 구현 요건**이다.

## 5. 지울 수 있게 되는 intrinsic 캡처 — **열 개이고, 수를 주장하지 않는다**

AGENTS.md 는 10차에 「캡처 여덟 개」라고 적는다. 세어 보면 **렌더러 8 + `policy-source.ts` 2 =
열**이다(뒤의 둘은 11차의 「파일 경계도 없다」가 추가한 것이다).

```
bin/heliopause-policy-render.ts:120  zoneMismatchIsOurs      = WeakSet.prototype.has.bind(...)
bin/heliopause-policy-render.ts:121  rememberOurZoneMismatch = WeakSet.prototype.add.bind(...)
bin/heliopause-policy-render.ts:144  RealError = Error
bin/heliopause-policy-render.ts:183  toText    = String
bin/heliopause-policy-render.ts:193  arm       = setTimeout
bin/heliopause-policy-render.ts:194  disarm    = clearTimeout
bin/heliopause-policy-render.ts:195  readClock = Date.now
bin/heliopause-policy-render.ts:196  toJson    = JSON.stringify
src/policy-source.ts:53              parseJson = JSON.parse
src/policy-source.ts:54              writeJson = JSON.stringify
```

🔴 **「전부 지울 수 있다」고 적지 않는다.** 캡처가 필요한지는 **그 코드가 정책 모듈과 같은 realm
에서 도는지**에 달려 있고, 그것은 **§3-a 의 미결정 사항**이다. 일반적인 장치를 만들면 그 범위에
대한 주장이 공짜로 생기고 그 주장은 검증되지 않는다 — 이 저장소가 세 라운드 연속 거기서 틀렸다.

구현의 규칙은 이렇게 한다: **§3-a 가 정해진 뒤, 캡처를 하나씩 되돌려 빨개지는 테스트 이름을
적는다.** 되돌려도 초록인 캡처는 지운다.

## 6. 격리는 **더 좁아진다** — #89 의 C1 우려와 반대 방향

**측정**(2026-10-06, node 26.4.0): 부모에 `LEAK89_SECRET` 을 심고 워커가 보는 env 를 셌다.

| 워커 옵션 | 워커가 보는 변수 수 | 비밀이 보이는가 |
|---|---|---|
| 기본 | **68** | **보인다** |
| `env: {}` | **0** | 안 보인다 |
| `env: { 필요한 것만 }` | **1** | 안 보인다 |

→ #89 의 「worker 는 기본적으로 부모의 env 를 복사한다」는 맞다. 다만 **`env: {}` 로 지금보다
좁게** 만들 수 있다. 렌더러에는 자격증명을 들지 않는다는 기동 검사가 있으니, 결과는
**지금과 같은 노출이 아니라 더 작은 노출**이다.

평가에 실제로 필요한 env 는 **구현 시 측정해서 정한다** — 지금 목록을 적으면 그것이 검증되지
않은 주장이 된다.

## 7. 비용 — 평가당 약 10배

**측정 기준**: 타임드 루프 **안에 GC 없음**. 첫 회를 따로 적는다(스레드·로더 기동을 평균에 섞지
않기 위해). node 26.4.0, darwin, 20회 평균.

```
워커        첫 41.7 ms · 그 뒤 17.9 ms/평가
인프로세스  첫  2.2 ms · 그 뒤  1.7 ms/평가
```

발행 1회(세 사이트)에 **약 54 ms 대 5 ms**.

### 콘솔 경로에 주는 영향

렌더러는 **요청이 올 때만** 평가한다(운영 관측 1-d 가 그것을 보였다 — 커밋이 들어와도 콘솔을
열지 않으면 평가가 없다). 그래서 이 50 ms 는 **스탬프가 움직인 뒤 첫 `/source` 요청 하나**에
붙는다. 캐시 적중은 평가하지 않으므로 영향이 없다.

⚠️ **스탬프가 움직였는데 여러 사이트를 한꺼번에 평가하는 경로**(기동 검증)에서는 직렬 합계가
된다. 지금 그 자리는 「각 promise 를 먼저 다 시작해 놓고 순서대로 await」인데(11차에서
`Promise.all` 을 버린 이유), 워커가 여럿 동시에 뜨면 **메모리 피크가 평가 수만큼** 된다.
동시도를 제한하는지는 **구현 결정**이고, 재지 않았다.

## 8. 롤아웃·롤백

이 변경은 **렌더러 한 프로세스 안**이다. 와이어 형식(`PolicySource`)도 `POLICY_SOURCE_SCHEMA` 도
바뀌지 않으므로, **매니저와 따로 굴려도 창이 생기지 않는다.**

| 단계 | 하는 것 | 되돌리는 법 |
|---|---|---|
| 1 | 워커 경로를 **env 플래그 뒤에** 넣어 배포(기본 꺼짐) | 아무것도 안 바뀐다 |
| 2 | 플래그를 켜고 1-d 와 같은 기준으로 **working set 과 평가 수**를 15분 간격으로 본다 | 플래그를 끈다 — **이미지 롤백 없이** |
| 3 | 계단이 사라진 것을 보고 플래그와 인프로세스 경로를 지운다 | 그 지점부터는 이미지 롤백 |

🔑 **2단계의 확인 기준을 미리 정한다**: 평가 수가 늘어도 working set 계단이 **1 Mi 해상도 안에서
안 보이는 것.** 1-d 가 적은 한계(`≈0` 계단을 GC 와 해상도로 가를 수 없음) 때문에 **「0 이다」는
확인할 수 없고**, 「계단이 더 이상 평가 수를 따르지 않는다」가 확인할 수 있는 것이다.
